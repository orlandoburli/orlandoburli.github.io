Migrating an ERP from HBase to Google BigTable: Schema Patterns from Production

A practitioner's notes on moving years of operational data from on-prem HBase to managed BigTable. Row keys, hot rows, dual-writes, and what we wish we had known sooner.

By Orlando Burli Junior · Senior Software Engineer at Rocket Lawyer
TL;DR Migrating an ERP datastore from self-managed HBase to Google Cloud BigTable is less about the technical migration itself and more about getting the schema right. Row-key design that worked on HBase can create hot spots on BigTable. Our team migrated a multi-terabyte ERP system serving thousands of business transactions per day. This article covers the schema decisions, the dual-write migration strategy, and the production incidents that taught us the most.

The Starting Point: HBase on Prem

When I joined the team, the core ERP datastore was running on a self-managed HBase cluster in a co-located data center. It had been in production for several years and stored hundreds of terabytes across dozens of column families. The setup worked — mostly. But the operational burden was real: namenode failovers required manual intervention, region server splits caused latency spikes during business hours, and scaling required hardware procurement cycles measured in months.

The business case for migrating to BigTable was clear:

  • Managed operations. No more paging the SRE at 3 AM because a region server hit its heap limit.
  • Automatic scaling. BigTable adds and removes nodes based on load, with a minimum configured cluster size.
  • Replication and backups. Built-in replication across zones and point-in-time recovery within a configurable window.
  • Consistent performance. No garbage-collection pauses, no region-split storms.

The migration wasn't optional — it was a prerequisite for moving other parts of the infrastructure off-prem and onto GCP's native data services.

Row-Key Design: The Hardest Part

HBase and BigTable share the same data model — a sparse, distributed, sorted map — but their performance characteristics differ in ways that make schema porting non-trivial. The single most impactful decision in any BigTable schema is the row key.

In HBase, the region server architecture handles hot spots through manual region splits and distribution. In BigTable, there are no region servers to tune. The tablet server distributes rows by key range, and a sequential or monotonically-increasing key pattern creates a single-node hot spot — one tablet server handles all writes while the others sit idle.

Our legacy HBase schema used a sequential row key pattern:

# HBase — problematic for BigTable
customer_{customer_id}          → Customer profile columns
order_{order_id}                → Order columns
invoice_{invoice_id}            → Invoice columns

This was fine on HBase with 40 pre-split regions. On BigTable, it would have given us approximately 5% node utilization on writes. Every new customer, order, or invoice went to a single tablet.

Salting: The Production Fix

The standard solution is salting — prepending a hash prefix to the row key to distribute writes across the key space.

# BigTable — salted row key
{hash_prefix}:customer_{customer_id}
{hash_prefix}:order_{order_id}
{hash_prefix}:invoice_{invoice_id}

We chose a two-byte hex hash of the natural key's MD5, taking the first four hex characters. This gives 65,536 possible shards, which is far more than our node count but allows the tablet server to distribute evenly:

private static String salt(String naturalKey) {
    byte[] digest = MessageDigest.getInstance("MD5")
        .digest(naturalKey.getBytes(StandardCharsets.UTF_8));
    return String.format("%02x%02x", digest[0] & 0xFF, digest[1] & 0xFF);
}

// Row key: "a3f1:customer_550e8400"
String rowKey = salt(customerId.toString()) + ":customer_" + customerId;

The colon delimiter is not required by BigTable, but it makes row-key scans with partial-prefix filters significantly easier during debugging and manual queries.

Warning: do not use a random number or timestamp as the salt prefix. Random salts mean reads must scan all shards. Deterministic salts (hash of the natural key) let you compute the exact row key for point lookups — same salt function, same result every time.

Column Families vs. Wide Rows

BigTable charges per column family for I/O, and each family is stored in a separate SSTable. Having too many column families increases read amplification. Having too few makes schema evolution harder.

Our HBase schema had 14 column families, mostly because different teams had added features over the years without consolidation. For BigTable, we reduced to 4:

Column Family Contents GC Policy
meta Row type, version, schema marker Keep 1
data Primary business attributes (customer profile, order items, invoice lines) Keep 1
audit Change history, last-modified-by, timestamps Max versions: 10
idx Secondary index entries for scan patterns Keep 1

The idx family deserves special mention. BigTable has no secondary indexes. If you need to look up orders by customer_id (where the primary row key is order_id), you write a secondary index row yourself:

// Primary row
a3f1:order_ord_001   data:customer_id = "cust_550e"
                     data:total = "1250.00"

// Index row — same customer_id prefix for collocation
a3f1:idx_by_customer/cust_550e/ord_001 = ""

The empty value on the index row keeps storage minimal. Scans over idx_by_customer/cust_550e/ give you all orders for that customer. This pattern is fast, explicit, and trivially debuggable with cbt or the Cloud Console.

The Migration Strategy: Dual-Writes with Verification

We migrated over several months using a dual-write pattern that avoided any extended cutover window.

Phase 1: Dual-Write (Weeks 1–6)

Every write went to both HBase and BigTable simultaneously. Reads still served from HBase. Verification ran as a background job comparing a random sample of rows every hour:

@Scheduled(fixedDelay = 60_000)
public void verifySample() {
    List<String> sample = sampleActiveRows(100);
    for (String rowKey : sample) {
        Row hbaseRow = hbaseClient.get(rowKey);
        Row bigtableRow = bigtableClient.readRow(rowKey);
        if (!rowsMatch(hbaseRow, bigtableRow)) {
            alertService.send("MISMATCH: " + rowKey);
            bigtableClient.writeRow(hbaseRow); // repair
        }
    }
}

This phase caught dozens of edge cases — encoding differences (HBase stores bytes, BigTable expects specific type encoding), timestamp granularity mismatches, and empty-vs-null semantics.

Phase 2: Read-Your-Writes (Weeks 7–8)

We flipped a feature flag per service. New reads from the writer process went to BigTable first, falling back to HBase on miss or error. Read-only services (reporting, analytics) stayed on HBase.

Phase 3: Full Cutover (Week 9)

All reads and writes pointed to BigTable. HBase was kept as a read-only fallback for two weeks, then decommissioned. The total data migration — about 4 TB of active rows plus 12 TB of archived data — completed within the dual-write phase. We never needed a bulk export-import.

The Incident That Taught Us About Read Throttling

Two days after Phase 2 started, we saw elevated p95 latency on the order-lookup endpoint. The cause: a reporting job was scanning the entire idx_by_customer prefix range every 15 minutes, consuming all available BigTable IOPS on that table.

BigTable throttles at the table level, not per-client. A single greedy scan can degrade latency for all other clients on the same table. The fix was two-fold:

  • Application-level prioritization. Report generation was moved to a dedicated BigTable instance that replicated via BigTable replication. The replica had lower throughput capacity and lower cost.
  • Read budget enforcement. Each service had a maximum read operations-per-second configured through a centralized rate limiter backed by a token bucket. This prevented any single service from starving the others.
Lesson: BigTable does not have per-query priority. A heavy scan from a background job will compete with user-facing reads. Isolate workloads by instance or enforce client-side rate limiting.

What We Wished We Had Known Sooner

  1. Test at production scale before migration. Our load tests at 10% volume looked fine. At 100%, we discovered that certain scan patterns that took 200 ms on HBase took 2 seconds on BigTable because the row-key prefix was not selective enough.
  2. BigTable replication is not instant. Cross-region replication has a typical lag of 5–15 seconds. If your disaster recovery plan assumes RPO near zero, test it end-to-end with your exact schema and access patterns.
  3. Monitor tablet-server imbalance. The Cloud Monitoring dashboard for BigTable shows per-server load. If one server handles more than 20% of requests, your row keys are hot. We saw this for our customer-profile rows until we increased the salt length from 1 byte to 2 bytes.
  4. Budget for schema iteration. Despite months of design, we changed the column family layout three times during dual-write. BigTable's schema-on-read model made this painless — we just stopped writing to the old families and started writing to the new ones. The old data remained queryable.
  5. cbt is your friend. The cbt CLI tool saved countless hours of debugging. Being able to cbt read mytable prefix=a3f1:customer_ from a Cloud Shell in under a second beats writing ad-hoc code every time.
