Production RAG with Gemini: Five Things the Tutorials Skip

Chunking, reranking, cost control, hallucination defenses, and the evaluation loop — five lessons from running a customer-facing RAG system on Gemini for over a year.

By Orlando Burli Junior · Senior Software Engineer at Rocket Lawyer
TL;DR Every RAG tutorial shows you how to embed documents and ask a question. None of them tell you what happens when your users ask questions your knowledge base cannot answer, when your embedding costs hit five figures, or when the model confidently invents a legal citation that looks real. This article covers five production lessons from building and operating a customer-facing RAG system on Google Gemini — the stuff that emerges after the demo works and the real users show up.

The Setup: Customer 360 at Rocket Lawyer

Our team built a conversational AI layer over a unified customer intelligence platform — we called it Customer 360. The system ingests customer interactions across multiple channels (support tickets, product usage telemetry, billing history, email threads) and lets customer-facing teams ask natural-language questions about any account.

The stack: Gemini Pro for LLM inference, text-embedding-004 for vector embeddings, AlloyDB for PostgreSQL with the pgvector extension, and a Retrieval-Augmented Generation (RAG) pipeline that pulls relevant context from the customer's interaction history before passing it to the model.

The demo worked in three days. The production system took nine months to stabilize. Here is what we learned.

1. Chunking Strategy Is Not a One-Liner

The first RAG tutorial you read tells you to split documents into 512-character chunks with 128-character overlap. That works for Wikipedia articles. It fails for support-ticket threads where a single "conversation" spans six back-and-forth messages, each referencing previous context.

What we tried, in order:

  • Fixed-size chunks (512 chars). Lost conversation boundaries. A single ticket's resolution would be split across chunks, and the retrieval would return the middle of the conversation without the setup or the conclusion.
  • Semantic chunking (by paragraph). Better, but a support thread with short replies collapsed into one or two chunks of very different lengths. The chunk containing the customer's initial description would be long; the chunk with the agent's "we fixed it" would be six words.
  • Conversation-aware chunking. We grouped messages by conversation_id and thread_id, then split within each thread at natural turn boundaries — but only if the turn exceeded 800 characters. Turns shorter than that were merged with the adjacent turn. This preserved conversational context while keeping chunks large enough to be semantically meaningful.
// Pseudo-code for conversation-aware chunking
for each conversation:
    for each thread (sorted by timestamp):
        buffer = ""
        for each message in thread:
            buffer += message.text + "\n"
            if buffer.length > 800 && message.is_turn_boundary:
                emit(buffer.trim())
                buffer = ""
        if buffer.trim().length > 100:
            emit(buffer.trim())

The result was a 23% improvement in retrieval recall at top-3 (from 0.61 to 0.75) compared to fixed-size chunking on our evaluation set.

2. Reranking Is Not Optional

Cosine similarity on embeddings gives you semantically close results. It does not give you the most useful results. A ticket that says "my payment failed" and a ticket that says "payment succeeded" have similar embeddings because they share vocabulary and structure, but they answer fundamentally different questions.

After the initial vector search returns the top-K candidates (we used K=20), we pass them through a reranker that scores each candidate by how well it actually answers the query. The reranker is a smaller cross-encoder model that takes the query and each candidate as a pair and outputs a relevance score.

def retrieve_and_rerank(query: str, k: int = 5) -> list[Chunk]:
    # Stage 1: embedding similarity (cheap, broad)
    candidates = vector_store.similarity_search(
        embedding=embed(query),
        k=20
    )

    # Stage 2: cross-encoder reranking (expensive, precise)
    scored = reranker.rerank(
        query=query,
        documents=[c.text for c in candidates]
    )

    # Return top-k after reranking
    return [candidates[s.index] for s in scored[:k]]
Cost note: we run the reranker on a dedicated TPU-v5-lite pod slice. The embedding search costs pennies per day. The reranker costs about $40/day at our throughput. Without it, the LLM would hallucinate significantly more often because the retrieved context would include irrelevant-but-semantically-similar chunks. The reranker pays for itself in reduced hallucination risk alone.

3. Hallucination Defenses: Three Layers

Our users ask questions about legal documents and billing records. An incorrect answer is not just embarrassing — it can cause real-world consequences. We built three layers of defense against hallucination:

Layer 1: Retrieval Grounding

The system is explicitly refused to answer from its training data. Every prompt includes a hard instruction:

You are a customer intelligence assistant. You answer questions ONLY
based on the retrieved context below. If the context does not contain
the information needed to answer, say "I cannot answer that based on
the available information." Do NOT use your pre-training knowledge to
fill gaps.

Retrieved context:
{context}

Question: {query}
Answer:

This sounds obvious, but we tested versions without the explicit prohibition and observed a 3× increase in fabricated answers — the model would supplement retrieved context with "common knowledge" about billing practices that did not apply to this customer.

Layer 2: Factual Consistency Check

Before returning the answer to the user, we run a second LLM call asking: "Does the answer contain any specific claims (dollar amounts, dates, status changes) that are NOT supported by the retrieved context?" If yes, the answer is rejected and the user sees a fallback response.

def check_factual_consistency(answer: str, context: str) -> bool:
    prompt = f"""
    Context: {context}
    Answer: {answer}

    Does the answer contain claims NOT supported by the context?
    Pay special attention to: dollar amounts, dates, policy names, statuses.
    Answer only YES or NO.
    """
    result = gemini_model.generate_content(prompt)
    return result.text.strip().upper() != "YES"

This catches about 15% of hallucinated answers in production. It adds ~600 ms of latency and one extra Gemini call per query. We consider it insurance.

Layer 3: Citation Injection

Every answer includes explicit citations back to the source documents. The model is instructed to include the [chunk_id] at the end of each factual claim. The UI renders these as clickable links to the original support ticket or billing record:

"Customer's current plan is Business Plus [chunk_47a23f], last payment of $299 was on March 15, 2026 [chunk_81c0e2]."

If a claim cannot be cited, it is not included in the answer. This transforms hallucination from a model quality problem into a UI transparency feature: users see exactly what information the answer is based on.

4. Embedding Cost Does Not Scale Linearly

At prototype scale (10k documents, 50 queries/day), embedding costs were negligible. At production scale (2M documents, 50k queries/day), embedding became our third-largest GCP cost after BigTable and Gemini inference.

The math:

  • Indexing embeddings: 2M documents × average 4 chunks each = 8M embeddings × 768 dimensions × 4 bytes = ~24 GB of vector data. Generating these cost about $300 in embedding API calls.
  • Query embeddings: 50k queries/day × 1 embedding per query = $15/day in embedding costs at text-embedding-004 pricing.
  • Reranking: 50k queries × 20 candidates × cross-encoder inference = additional compute.

We optimized in three ways:

  1. Document-level caching. If the same document is updated (e.g., a support ticket gets a new reply), we only re-embed the new chunk, not the entire document.
  2. Query embedding caching. Identical queries from different users (e.g., "what is this customer's plan?") are deduplicated for 5 minutes. At the rate our agents search, this eliminated ~40% of query embedding calls.
  3. Dimensionality reduction. We experimented with reducing from 768 → 256 dimensions using Matryoshka embedding truncation. The recall-at-10 dropped by only 2.3%, but the vector storage cost dropped by 66% and query embedding latency dropped by 40%. We kept the truncation.

5. The Evaluation Loop Never Stops

RAG evaluation is not a one-time benchmark. We built a continuous evaluation pipeline that runs twice a week.

The flow:

  1. Gather golden Q&A pairs. Customer support managers highlight 10–15 queries per week where the system answered wrong. These become new evaluation cases.
  2. Run the evaluation batch. 500 curated query-context-answer triples are run against the current pipeline. Metrics: retrieval recall, answer faithfulness, latency p95, cost per query.
  3. A/B test changes. A new chunking strategy, a different reranker checkpoint, a revised prompt template — each change runs through the evaluation batch before reaching production.
  4. Regression alert. If any metric drops by more than 5% compared to the previous run, the deploy is blocked and the team investigates.
# Evaluation metric: Answer Faithfulness
# What fraction of claims in the answer are supported by the retrieved context?
def faithfulness_score(answer: str, context: str) -> float:
    claims = extract_claims(answer)  # split on " [chunk_...]"
    if not claims:
        return 1.0
    supported = sum(
        1 for c in claims
        if claim_is_supported_by_context(c, context)
    )
    return supported / len(claims)

Over nine months, our faithfulness score improved from 0.82 to 0.96. The final 4% are cases where the context genuinely contains contradictory information (e.g., a billing record shows two different payment methods on the same date). We accept those as data-quality issues rather than RAG failures.
