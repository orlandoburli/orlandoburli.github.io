Production RAG with Gemini: Five Things the Tutorials Skip

Every RAG tutorial stops at similarity_search(query). Production starts there. Here are five lessons from running Gemini in front of real customers.

Orlando Burli Júnior · Senior Software Engineer · ~12 min read
TL;DR Naive RAG works in a notebook. In production it hallucinates, costs more than expected, returns irrelevant snippets, and gets worse silently. The five things that actually move the needle: chunking strategy beats embedding model selection; reranking is non-optional past a few thousand documents; cost explodes if you do not cache and batch; hallucination defenses live in the prompt and the retrieval, not in the model; and you cannot improve what you do not measure.

The setup

The system this article is based on is a customer intelligence platform that lets internal users ask questions about an account in natural language. Behind it: hundreds of thousands of documents per tenant, a Gemini-based answer pipeline, pgvector for storage, a reranker in the middle. Tens of thousands of queries per week from real humans who notice when answers are wrong.

What follows is what we learned building and running it for a year. None of it is in the introductory tutorials. All of it matters.

Lesson 1: Chunking beats embedding model selection

Engineers love to debate embedding models. Should we use text-embedding-004? Switch to gemini-embedding-001? Try an open model? In our experience, the chunking strategy moved retrieval quality more than swapping any of these.

The reason is simple: an embedding is a summary of the text it ingests. If your chunks are 2,000 tokens of mixed-topic text, the embedding is a blurry average of everything in the chunk. The vector cannot point sharply at the answer because the chunk does not.

What we tried

Strategy Recall@10 Notes
Fixed 1,000 tokens, 0 overlap baseline Splits sentences, loses context at boundaries
Fixed 500 tokens, 100 overlap +12% Recovers most boundary losses; doubles index size
Sentence-aware splitter, 500 token soft cap +18% Respects sentence boundaries; needs a tokenizer
Document-structure-aware (split on headings, paragraphs, list items) +27% Largest gain; requires document-type-specific parsers
Same as above + a 1-line summary prepended to each chunk +34% The single biggest improvement we made all year

The last row is the surprising one. We generate a one-sentence summary of the parent document and prepend it to every chunk before embedding. The chunk's embedding now encodes both local content and global context. Retrieval of "What was the customer's outcome on this case?" works even when the chunk itself does not mention the customer name, because the document context does.

This is cheap. The summary is generated once per document at ingestion time and reused for every chunk.

Lesson 2: Reranking is non-optional past a few thousand documents

Vector similarity is fast and approximate. It returns the K nearest chunks to the query embedding in vector space. That is correlated with relevance, but not the same thing. Past a few thousand chunks per tenant, the top 10 results from pure vector search start to include semantic near-misses that look right and are wrong.

The fix is a two-stage retrieval:

  1. Recall stage — retrieve top 50 candidates with vector search. Optimize for "the right answer is somewhere in this set", not "the right answer is at position 1".
  2. Precision stage — rerank those 50 with a cross-encoder model. Take the top 5 of the reranked list.

A cross-encoder runs the query and each candidate together through a model that scores their relevance jointly. It is much more accurate than the cosine of two independently-computed embeddings. It is also much slower per pair, which is exactly why you only run it on 50 candidates rather than the full corpus.

from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

def retrieve(query: str, tenant_id: str, k: int = 5) -> list[Chunk]:
    candidates = vector_store.similarity_search(
        query, k=50, filter={"tenant_id": tenant_id}
    )
    pairs = [(query, c.text) for c in candidates]
    scores = reranker.predict(pairs)
    ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])
    return [c for c, _ in ranked[:k]]

For the platform this article is based on, the reranker improved end-to-end answer quality measurably more than upgrading the embedding model or the LLM. Order of magnitude: a 30% reduction in user-flagged "wrong answer" feedback after we shipped reranking.

If you do not want to run a model yourself, a Gemini call with a structured prompt can serve as a reranker too — slower and more expensive, but no infrastructure.

Lesson 3: Cost explodes if you do not cache and batch

Embedding tokens look cheap on the price page. They become expensive when you multiply by document count, chunk count, and the rate at which you re-embed.

Three habits cut our embedding bill by more than half:

Cache embeddings on content hash

Documents do not change as often as ingestion pipelines re-run. Hash the chunk text, key the cache by hash, store the embedding. If the same chunk shows up tomorrow, do not pay to re-embed it.

import hashlib

def get_or_create_embedding(text: str) -> list[float]:
    key = hashlib.sha256(text.encode()).hexdigest()
    cached = redis.get(f"emb:{key}")
    if cached:
        return json.loads(cached)
    emb = embedding_client.embed(text)
    redis.set(f"emb:{key}", json.dumps(emb), ex=86400 * 30)
    return emb

Trivial code. Significant savings.

Batch embedding requests

Most embedding APIs accept a list of inputs in a single call and price per token, not per call. Concurrency is fine but waste is not. A bulk-ingest job that calls the API one chunk at a time is leaving money and throughput on the table:

def embed_batch(texts: list[str], batch_size: int = 100) -> list[list[float]]:
    out = []
    for i in range(0, len(texts), batch_size):
        out.extend(embedding_client.embed(texts[i:i + batch_size]))
    return out

Set a hard quota guard

The most expensive bug in any LLM-based system is an infinite loop. A retry loop without a backoff multiplier, a workflow that re-ingests a tenant on every webhook, a cache miss under high traffic — any of these can multiply your token spend by an order of magnitude before you notice. A daily token budget enforced at the gateway, with hard rejects when exceeded, has paid for itself multiple times.

Lesson 4: Hallucination defenses live in the prompt and the retrieval

The instinct is to "fix" hallucinations by switching to a smarter model. Bigger models do hallucinate less, but the larger gain comes from prompt and retrieval discipline. Three patterns we ship in production:

Grounding instructions with explicit refusal

Every answer prompt includes a contract:

You are answering questions about a customer account.
Use ONLY the information in the CONTEXT block.
If the CONTEXT does not contain enough information to answer the
question, respond with exactly: "I do not have enough information
in the available records to answer this confidently."

CONTEXT:
{retrieved_chunks}

QUESTION: {user_question}

Format your answer with citations like [1], [2] referring to the
numbered context blocks above.

The refusal sentence is verbatim and trained into the eval set. We measure how often the system correctly refuses on questions whose answers are not in the corpus, alongside accuracy on questions whose answers are.

Citation enforcement

The prompt requires [1], [2] citations. The application parses the answer, validates that each citation index maps to a real retrieved chunk, and rejects the answer if it does not. An answer that cites a chunk that was not retrieved is a hallucination by definition; we surface it as a regeneration retry rather than show it to the user.

Confidence thresholds on retrieval

If the top reranker score is below a threshold, do not call the LLM at all. Return the refusal sentence directly. This is faster, cheaper, and more honest than asking a model to produce an answer from low-quality context. The threshold is calibrated against the eval set quarterly.

Lesson 5: You cannot improve what you do not measure

The hardest part of running RAG in production is that the system can degrade silently. A new document type is ingested and embeds badly. A reranker model release shifts score distributions. A prompt edit subtly changes refusal behavior. Without measurement, you find out from a user complaint, weeks late.

The minimum viable evaluation loop:

A frozen evaluation set

200 to 500 question-and-expected-answer pairs, drawn from real user queries, curated by humans, version-controlled. Run the full RAG pipeline against this set on every meaningful change. Track three metrics:

  • Faithfulness — does the answer make claims supported by the retrieved context?
  • Answer relevancy — does the answer address the question?
  • Context precision — were the retrieved chunks actually relevant to the question?

Tools like RAGAS implement these as LLM-as-judge metrics. They are imperfect — using an LLM to grade an LLM has obvious limitations — but they correlate well with human judgment in our experience, and they are cheap enough to run on every change.

A user feedback loop

Every answer surfaces a thumbs-up / thumbs-down. The downvotes are gold: each one is a candidate for the eval set, a hint at a weak document type, or a prompt edge case. The application logs the full retrieval context with each downvoted answer, so investigation does not require reproducing the query.

Drift monitoring

Track the distribution of reranker scores over time. A sudden shift downward usually means content quality degraded — a new document source ingested with bad chunking, an embedding model version changed, a tenant uploaded a corpus that does not look like the rest. Distribution drift catches problems before users do.

The recommended starting stack

For a team standing up RAG today, the boring stack works:

  • Storage — PostgreSQL with pgvector. Until you have tens of millions of vectors per tenant, this beats specialized vector DBs on operational simplicity.
  • Embeddings — Gemini's text-embedding-004 with the appropriate task type (RETRIEVAL_DOCUMENT at ingest, RETRIEVAL_QUERY at query time). The task type matters; do not skip it.
  • Reranker — a cross-encoder like BAAI/bge-reranker-v2-m3 served on a small GPU instance, or Gemini-as-reranker if you cannot run inference yourself.
  • Generator — Gemini 1.5 Pro or Flash depending on the latency / cost profile. Flash is good enough for most extractive answers.
  • Eval — RAGAS for LLM-as-judge metrics, plus a hand-curated golden set kept in version control.

Avoid premature optimization. Get the chunking right first. Add reranking when vector search alone stops cutting it. Move to a managed vector DB only when pgvector becomes a bottleneck — not before.

Closing

RAG is one of the few areas in software where the gap between a working demo and a production system is measured in months. The demo is genuinely easy. The production system requires the same discipline as any other distributed data pipeline: cache what you can, batch what you must, measure everything, and design for graceful degradation when the model is unsure.

None of these lessons are difficult. None of them are in the tutorials. All of them are the difference between a system you trust enough to put in front of customers and a system that quietly embarrasses you.
