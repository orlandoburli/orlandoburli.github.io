Event-Sourced Recommendation Engines

Tutorials show the model. Production recommendation systems live and die on the event pipeline. Here is the architecture of one we built — events, features, training, and the serving path.

Orlando Burli Júnior · Senior Software Engineer · ~13 min read
TL;DR A recommendation system is mostly a data pipeline with a model attached. Get the events right and the model is straightforward. Get the events wrong and no model can save you. This is the architecture of a production recommendation engine — a single source-of-truth event log, derived feature stores for offline and online use, periodic model training, and a low-latency serving path. The interesting decisions are at the seams between these components, not inside any one of them.

What we are recommending

The system this article is based on suggests next-best actions to customers — things they could do on the platform that align with their stated goals and prior behavior. Tens of thousands of users, millions of events per day, an inventory of a few hundred candidate actions. The model is a learning-to-rank classifier; the action space is small enough that we can score every candidate at request time. None of that detail is universal. The architecture around it is.

Five moving parts. Each replaceable. The contracts between them are the design.

The event log is the foundation

Every behavior signal the model could care about is a domain event published to a single Pub/Sub topic. The event schema is opinionated and small:

{
  "event_id": "uuid",
  "event_type": "ProductViewed",
  "user_id": "u_123",
  "occurred_at": "2026-04-18T10:13:25Z",
  "ingested_at": "2026-04-18T10:13:26Z",
  "session_id": "s_abc",
  "properties": {
    "product_id": "p_456",
    "category": "contracts",
    "source": "search"
  },
  "context": {
    "platform": "web",
    "country": "US",
    "experiment_assignments": ["rec_v3:treatment"]
  }
}

A few intentional choices here:

  • Both occurred_at and ingested_at. Late-arriving events are normal. Without both timestamps, you cannot tell whether a feature lookup is missing a recent event or a delayed one.
  • Schema is event-type-shaped, not table-shaped. Properties are nested, not flattened columns. New event types do not require schema migrations downstream — just a new feature job.
  • Experiment assignments in context. Critical for correctly attributing model predictions back to the cohort that was exposed to a given model version.

The events flow into a partitioned BigQuery table via a Dataflow Pub/Sub-to-BigQuery template. The table is append-only. There are no updates, no deletes (compliance erasure happens via a separate pseudonymization step). This is the system of record for "what happened".

Features: the same logic, two stores

A recommendation model needs the same features in two places: at training time (offline, big batches) and at serving time (online, single user, low latency). The single biggest source of bugs in recommendation systems is the same feature being computed slightly differently in those two paths.

The architectural answer is to write the feature logic once and materialize it into both stores. We did this with PySpark jobs that produce two outputs:

  1. A BigQuery table partitioned by date for training.
  2. A keyed write into Redis (or Bigtable, depending on the feature's TTL profile) for serving.

The job runs on a schedule for batch features and as a streaming job for near-real-time features. The contract — column names, types, semantics — is identical in both stores.

Feature freshness as a first-class concern

Every feature has a documented freshness SLA. "Days since last login" is allowed to be up to 6 hours stale. "Pages viewed in current session" must be sub-second fresh. The freshness budget drives the implementation:

Freshness SLA Implementation
Sub-second Computed at request time from session state in Redis
Sub-minute Streaming PySpark job consuming Pub/Sub, writing Redis
Sub-hour Hourly batch from BigQuery, written to Redis with TTL
Daily Nightly batch, served from BigQuery for training, Bigtable for serving

The freshness column lives in a feature catalog that the data scientists own. New model features are not allowed in production without a documented SLA and a corresponding implementation tier.

Training and the offline / online consistency check

Training runs on Vertex AI on a weekly cadence. The training set is constructed by joining historical events to the materialized features, with a strict point-in-time correctness rule: a feature value used to train on event E must not include any signal from after E's occurred_at. Violating this is the most common form of "data leakage" and produces models that look great offline and fail in production.

Two safeguards keep us honest:

1. Time-travel joins, not as-of joins on partition

The training query does not just join on date partitions. It uses an explicit WHERE features.computed_at <= events.occurred_at, which respects the feature's actual computation time, not the partition it landed in. Partition-only joins can leak signal from late-arriving events.

2. Online / offline parity check

A nightly job samples 1,000 recent serving requests, looks up the features that were served, and re-derives them from the offline store at the same timestamp. The difference distribution is a metric. If it drifts above a threshold, an alert fires. We have caught two genuinely subtle bugs this way — both were race conditions in feature materialization that nothing else would have surfaced.

The serving path

The model is served by a Spring Boot service. A request looks like:

  1. Receive a recommend call with a user ID and a context (page, intent).
  2. Fetch the candidate set — typically a few hundred items, pre-filtered for eligibility (region, plan, content licensing, etc.).
  3. Fetch the user's feature vector from Redis (single round-trip, all features in one hash).
  4. Fetch the candidate-side features from Bigtable (one batched read for all candidates).
  5. Score each candidate with the model.
  6. Apply business rules (diversity quotas, blacklists, cooldowns).
  7. Return the top N.

Performance budget: 50 ms p95 end-to-end. The expensive parts are the Bigtable batched read and the model scoring. Both are bounded — a few hundred items times a few dozen features each. The model itself is a gradient-boosted tree exported as ONNX and run with the ONNX runtime; inference is sub-millisecond.

@Service
@RequiredArgsConstructor
public class RecommendationService {

    private final CandidateProvider candidateProvider;
    private final UserFeatureStore userFeatures;
    private final ItemFeatureStore itemFeatures;
    private final OnnxScorer scorer;
    private final BusinessRules rules;
    private final RecommendationLogger logger;

    public List<Recommendation> recommend(String userId, RequestContext ctx) {
        List<String> candidates = candidateProvider.eligible(userId, ctx);
        UserFeatureVector userVec = userFeatures.fetch(userId);
        Map<String, ItemFeatureVector> itemVecs = itemFeatures.batchFetch(candidates);

        List<ScoredCandidate> scored = candidates.stream()
            .map(c -> new ScoredCandidate(c, scorer.score(userVec, itemVecs.get(c))))
            .sorted(comparingDouble(ScoredCandidate::score).reversed())
            .toList();

        List<Recommendation> result = rules.apply(scored, ctx).stream()
            .limit(ctx.requestedCount())
            .toList();

        logger.logRequest(userId, ctx, candidates, result);
        return result;
    }
}

The logger.logRequest call is non-negotiable. Every served recommendation is logged with the candidate set, the scores, the user features at serving time, and the model version. This becomes training data for the next iteration and the audit trail for "why did the model recommend X?" debugging.

Experimentation is part of the architecture

Recommendation systems live or die by their ability to A/B test. Building experimentation in as a first-class concept rather than a bolt-on saves enormous pain later.

The experiment framework integrates at three points:

  1. Assignment at request time — the user is bucketed deterministically into a treatment based on a stable hash of their ID, and the assignment is recorded in the request log.
  2. Treatment at scoring time — the assignment determines which model version (or candidate generator, or business rule set) is used.
  3. Analysis offline — the request log + downstream conversion events form the experiment data. A scheduled job computes the metrics that decide the experiment.

This is intentionally generic. Any change to the system — a new model, a new feature, a different ranking rule — goes through the same experiment pipeline. There is no "this is too small to test" path; there is also no "we tested this in staging" excuse.

What breaks first

If you build a system like this, the first things to break tend to be:

  1. Feature freshness alerts as the streaming PySpark job lags behind a traffic spike. Mitigation: scale the streaming job on watermark lag, not CPU.
  2. Online / offline drift when a feature is renamed in one path but not the other. Mitigation: feature catalog as code, with CI checks that both stores produce the registered columns.
  3. Bigtable hot rows when a single popular item is in every candidate set and its feature row gets hammered. Mitigation: cache hot item features in the serving JVM with a short TTL.
  4. Model staleness as user behavior drifts but the training schedule does not catch up. Mitigation: monitor a stability metric on the input feature distributions and trigger early retraining when drift exceeds a threshold.

None of these are model problems. All of them are pipeline problems. This is the recurring lesson of building these systems: the model is the easy part.

What we would do differently

  • Write the parity check first. The online / offline consistency job should exist before the first feature is served, even if it is checking a single feature. Adding it after the fact was harder than it should have been.
  • One event topic, not many. We started with topic-per-event-type and consolidated later. The single topic with a discriminator field is dramatically easier to reason about.
  • Treat the feature catalog as a contract. A markdown file is not a contract. A typed schema with CI enforcement is.
  • Build the request logger before the first model. Without it, your first iteration of the model is also your first iteration of the dataset, and the second iteration cannot improve because there is no labeled data yet.

Closing

Recommendation systems get romanticized as model engineering. In production they are mostly data engineering with a thin model layer on top. The architecture choices that matter — event log shape, feature store split, request logging, experiment integration — are made early, persist for years, and determine how much pain you will have for the rest of the system's life.

The model is the easy part. Everything around it is the architecture.
