Transactional Outbox with Spring Boot and Google Pub/Sub

Every outbox tutorial assumes Kafka. Here is the GCP version — the dual-write trap, a Postgres-backed relay, and the production details nobody publishes.

Orlando Burli Júnior · Senior Software Engineer · ~10 min read
TL;DR Saving to Postgres and publishing to Pub/Sub in the same Spring method is a dual-write. @Transactional does not save you. The fix is to write the event to an outbox table inside the same DB transaction, then have a separate relay publish it. This article walks through the schema, the relay using SELECT ... FOR UPDATE SKIP LOCKED, idempotency on the consumer side, and the metrics that matter in production.

The dual-write problem

This is the kind of code that looks innocent in code review:

@Service
public class OrderService {

    private final OrderRepository orderRepository;
    private final PubSubTemplate pubSubTemplate;

    @Transactional
    public Order placeOrder(NewOrderRequest req) {
        Order order = orderRepository.save(Order.from(req));
        pubSubTemplate.publish("orders", new OrderPlaced(order.getId()));
        return order;
    }
}

Two writes. One @Transactional annotation. What could go wrong?

Quite a lot. The transaction boundary belongs to the database. pubSubTemplate.publish() is an RPC to Pub/Sub — it does not roll back when the surrounding transaction does, and it does not commit when the transaction does either. Three failure modes lurk here:

  1. DB commit succeeds, Pub/Sub publish fails. The order exists in your database; downstream services never hear about it. Silent data divergence.
  2. Pub/Sub publish succeeds, DB commit fails. Downstream services act on a phantom order that does not exist. Customer service tickets follow.
  3. Pub/Sub publish succeeds, the JVM crashes before commit. Same as #2, with bonus log confusion.

Most teams do not notice this until it bites them in production at low frequency, which is the worst kind of bug. You cannot reliably reproduce it, but the data slowly drifts.

Why the obvious fixes do not work

Three things engineers usually try first, all of which look reasonable and all of which are wrong:

1. Reorder the calls

"Just publish first, then save." This is worse — now any DB failure leaves a published event with no record of what it referred to.

2. Use TransactionSynchronizationManager to publish after commit

TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override public void afterCommit() {
            pubSubTemplate.publish("orders", new OrderPlaced(order.getId()));
        }
    }
);

Better — the publish only happens if the DB commit succeeded. But it still fails if the JVM dies between commit and publish, or if Pub/Sub is unreachable at that moment. There is no retry, no record of intent.

3. Distributed transactions / XA

Pub/Sub does not support XA. End of discussion.

The outbox idea

The pattern is older than microservices and embarrassingly simple:

Inside the same database transaction, write the business row and a row to an outbox_events table describing the event. A separate process polls that table and publishes to Pub/Sub.

If the transaction commits, both rows are durable. If it rolls back, neither exists. The publish becomes asynchronous and retriable. The DB is the single source of truth for "did this event happen?"

The schema

I have used variations of this schema across multiple production systems. Keep it boring:

-- Flyway: V1__create_outbox.sql
CREATE TABLE outbox_events (
    id              UUID         PRIMARY KEY,
    aggregate_type  VARCHAR(64)  NOT NULL,
    aggregate_id    VARCHAR(64)  NOT NULL,
    event_type      VARCHAR(96)  NOT NULL,
    topic           VARCHAR(128) NOT NULL,
    payload         JSONB        NOT NULL,
    headers         JSONB        NOT NULL DEFAULT '{}'::jsonb,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    published_at    TIMESTAMPTZ,
    attempt_count   INT          NOT NULL DEFAULT 0,
    last_error      TEXT
);

CREATE INDEX idx_outbox_unpublished
    ON outbox_events (created_at)
    WHERE published_at IS NULL;

A few intentional choices worth flagging:

  • Partial index on unpublished rows only. The relay query hits this and stays small even when the table grows to millions of rows.
  • UUID primary key. The consumer uses this for idempotency, so it must be globally unique and assigned at write time.
  • JSONB payload. Schema evolution without migrations. Validate at publish time, not at write time.
  • No processed boolean. Use published_at IS NULL instead — gives you a free timestamp for lag metrics.

Writing to the outbox

Here is the corrected service. The important thing is that the outbox insert and the business insert use the same @Transactional boundary:

@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final OutboxEventRepository outboxRepository;
    private final ObjectMapper objectMapper;

    @Transactional
    public Order placeOrder(NewOrderRequest req) {
        Order order = orderRepository.save(Order.from(req));

        OutboxEvent event = OutboxEvent.builder()
            .id(UUID.randomUUID())
            .aggregateType("Order")
            .aggregateId(order.getId().toString())
            .eventType("OrderPlaced")
            .topic("orders")
            .payload(objectMapper.valueToTree(
                new OrderPlacedPayload(order.getId(), order.getCustomerId(), order.getTotal())
            ))
            .build();

        outboxRepository.save(event);
        return order;
    }
}

That is it for the producer side. No Pub/Sub client, no async callbacks, no retry logic. The service does one thing: persist intent atomically.

The relay

You have two real options:

Option When to pick it Trade-off
Debezium / Datastream CDC High-volume, multi-service, multi-region Operational cost — you are running a CDC pipeline
Spring @Scheduled poller Single service, modest volume (under a few thousand events per second per node) Adds DB load; you own the locking and the back-off

Most teams should start with the poller. It needs no new infrastructure, lives inside the same Spring Boot app, and is easy to debug. The trick is doing the polling correctly so that multiple replicas do not republish the same event.

The poller, correctly

@Component
@RequiredArgsConstructor
@Slf4j
public class OutboxRelay {

    private final OutboxEventRepository repository;
    private final PubSubTemplate pubSubTemplate;
    private final MeterRegistry meterRegistry;

    private static final int BATCH_SIZE = 100;
    private static final int MAX_ATTEMPTS = 10;

    @Scheduled(fixedDelayString = "${outbox.poll-interval-ms:500}")
    @Transactional
    public void publishBatch() {
        List<OutboxEvent> batch = repository.lockUnpublishedBatch(BATCH_SIZE, MAX_ATTEMPTS);
        if (batch.isEmpty()) return;

        for (OutboxEvent event : batch) {
            try {
                PubsubMessage msg = PubsubMessage.newBuilder()
                    .setData(ByteString.copyFromUtf8(event.getPayload().toString()))
                    .putAttributes("eventId", event.getId().toString())
                    .putAttributes("eventType", event.getEventType())
                    .putAttributes("aggregateId", event.getAggregateId())
                    .build();

                pubSubTemplate.publish(event.getTopic(), msg).get(5, SECONDS);

                event.setPublishedAt(Instant.now());
            } catch (Exception e) {
                event.setAttemptCount(event.getAttemptCount() + 1);
                event.setLastError(truncate(e.getMessage(), 500));
                log.warn("Outbox publish failed for {} (attempt {})",
                    event.getId(), event.getAttemptCount(), e);
            }
        }

        repository.saveAll(batch);
        meterRegistry.counter("outbox.published", "topic", "all")
            .increment(batch.stream().filter(e -> e.getPublishedAt() != null).count());
    }
}

The repository method is where most implementations get this wrong:

@Repository
public interface OutboxEventRepository extends JpaRepository<OutboxEvent, UUID> {

    @Query(value = """
        SELECT * FROM outbox_events
         WHERE published_at IS NULL
           AND attempt_count < :maxAttempts
         ORDER BY created_at
         LIMIT :batchSize
         FOR UPDATE SKIP LOCKED
        """, nativeQuery = true)
    List<OutboxEvent> lockUnpublishedBatch(
        @Param("batchSize") int batchSize,
        @Param("maxAttempts") int maxAttempts);
}

FOR UPDATE SKIP LOCKED is the magic. Multiple Spring Boot replicas can run this poller concurrently and each will pick a disjoint set of rows. No coordination service required, no Zookeeper, no leader election.

Idempotency on the consumer side

The outbox pattern guarantees at-least-once delivery, never exactly-once. A network blip between Pub/Sub acking your publish and your code marking the row as published will republish the event. Plan for it.

The simplest consumer-side defense is a deduplication table keyed on the event ID:

CREATE TABLE consumed_events (
    event_id    UUID         PRIMARY KEY,
    consumer    VARCHAR(64)  NOT NULL,
    consumed_at TIMESTAMPTZ  NOT NULL DEFAULT now()
);
@Transactional
public void handle(OrderPlacedMessage msg) {
    if (consumedEventRepository.existsById(msg.eventId())) {
        return;
    }
    consumedEventRepository.save(new ConsumedEvent(msg.eventId(), "billing-service"));
    billingService.chargeCustomer(msg.customerId(), msg.amount());
}

The insert and the business write are in the same transaction. If the business write fails, the dedup row rolls back too, and Pub/Sub will redeliver. If the business write succeeds but ack to Pub/Sub fails, the next delivery hits the dedup table and exits cleanly.

The metrics that matter

If you only export three metrics, make them these:

  • Outbox lag — now() - min(created_at) for unpublished rows. This is your north star. When this rises, something is broken.
  • Publish attempt count — distribution of attempt_count. Healthy systems sit at 1.0 average. Anything above 1.5 means you have a flaky topic or broker.
  • Stuck rows — count where attempt_count >= MAX_ATTEMPTS. These need a human. Set up an alert.

Expose them as Micrometer gauges:

@Component
@RequiredArgsConstructor
public class OutboxMetrics {

    private final OutboxEventRepository repository;
    private final MeterRegistry registry;

    @PostConstruct
    void register() {
        Gauge.builder("outbox.lag.seconds", repository, this::oldestUnpublishedAgeSeconds)
            .register(registry);
        Gauge.builder("outbox.stuck.count", repository,
                r -> r.countByAttemptCountGreaterThanEqual(10))
            .register(registry);
    }

    private double oldestUnpublishedAgeSeconds(OutboxEventRepository repo) {
        return repo.findOldestUnpublishedCreatedAt()
            .map(t -> (double) Duration.between(t, Instant.now()).getSeconds())
            .orElse(0.0);
    }
}

Pitfalls I have hit in production

Things that are obvious in hindsight:

  1. Outbox table grows unbounded. Add a nightly job that deletes published rows older than N days. Be liberal — keep them long enough for incident forensics.
  2. Long-running consumer transactions hold locks. If handle() is slow, the dedup row stays locked. Keep handlers tight; defer slow work to a follow-up task.
  3. Payload size. Pub/Sub caps messages at 10 MB. Postgres JSONB will happily store much larger. If you regularly produce big payloads, store the body in GCS and put the URI in the event.
  4. Topic ordering. Pub/Sub ordering keys work, but only with a regional endpoint. If you need ordered delivery, set orderingKey to the aggregateId when building the message.
  5. The relay is a noisy neighbor. A 500 ms poll across many replicas can hammer your DB. Stagger replicas with initialDelay or move to push-based CDC once you scale.

When to graduate to CDC

The poller is good until it is not. Switch to a CDC-based relay (Debezium reading the WAL, or Datastream piping into Pub/Sub directly) when:

  • You consistently publish more than a few thousand events per second per service.
  • Your DB load from the poller becomes measurable on dashboards.
  • You have multiple services with outbox tables and want a single, uniform relay infrastructure.

The producer-side code does not change. That is the elegance of the pattern — the outbox table is the contract, and the relay is an implementation detail.

Closing

The outbox pattern is one of those rare things in distributed systems where the right answer is also the simple answer. A table, a poller, a dedup check on the consumer. No magic. No new dependencies if you are already running Postgres and Spring Boot.

If you take one thing away from this article: do not publish to a message broker inside a database transaction and call it a day. The CAP theorem does not negotiate, and dual-writes will find you eventually.
