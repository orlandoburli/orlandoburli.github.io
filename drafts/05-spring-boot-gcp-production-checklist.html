Spring Boot on GCP: The Production Checklist Nobody Publishes

Twenty things to verify before your Spring Boot service hits real traffic on Google Cloud. None of them are interesting individually. All of them have caused outages somewhere.

Orlando Burli Júnior · Senior Software Engineer · ~11 min read
TL;DR Spring Boot on GCP works out of the box for the demo. The gap between the demo and production is filled with small decisions that look fine in staging and become outages with real traffic. This is the checklist I run through before every new service goes live — startup behavior, observability, secrets, networking, autoscaling, and the operational details that nobody writes down.

How to use this checklist

The list is grouped by category. Each item is short on purpose — if a section needs a deeper explanation, it gets a paragraph; if it does not, it gets a bullet. None of these are theoretical. Every one represents a real incident I have either lived through or watched a team live through.

Treat it as a pre-flight checklist, not a tutorial. Walk through it once before you go live, then again every six months as the service evolves.

Startup and shutdown

1. Health check endpoints, separated by purpose

Spring Boot Actuator gives you /actuator/health. The default lumps liveness and readiness together, which is wrong. Configure them separately:

management:
  endpoint:
    health:
      probes:
        enabled: true
      group:
        liveness:
          include: livenessState
        readiness:
          include: readinessState, db, pubsub

Liveness is "the JVM is responsive". Readiness is "I can serve traffic". Mixing them causes Kubernetes to restart pods that are temporarily unable to reach a dependency, which makes the dependency outage worse.

2. Graceful shutdown

server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s

On a SIGTERM (which GKE sends before killing a pod), in-flight requests get up to 30 seconds to complete. Without this, every deployment drops a percentage of requests equal to your concurrency. Customers notice.

3. Pre-stop hook on the pod

Even with graceful shutdown, the pod is removed from the service immediately on termination. Add a small pre-stop sleep so the load balancer has time to stop sending new traffic before SIGTERM fires:

lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 5"]

4. Startup probe with realistic budget

JVM applications are slow to start. A liveness probe with a 30-second initial delay will kill a pod that needed 35 seconds to warm the JIT. Use a startup probe instead — it gives the JVM a generous warmup window before liveness takes over:

startupProbe:
  httpGet: {path: /actuator/health/liveness, port: 8080}
  failureThreshold: 30
  periodSeconds: 5

Observability

5. Structured logging in JSON

Cloud Logging extracts structured fields automatically when log lines are JSON. Use Logback's encoder or the logstash-logback-encoder dependency:

<appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
  <encoder class="net.logstash.logback.encoder.LogstashEncoder">
    <customFields>{"service":"orders-api"}</customFields>
  </encoder>
</appender>

Now jsonPayload.severity, jsonPayload.thread_name, jsonPayload.logger_name, and any MDC values are queryable in Cloud Logging directly. Without this, you are grep-ing free text.

6. Trace context propagation

Add spring-cloud-gcp-starter-trace and your service emits OpenTelemetry traces to Cloud Trace automatically. Crucially, the W3C trace context header propagates through outbound RestClient / WebClient calls, which means a request that touches three services produces one trace, not three.

7. The four metrics that matter

Wire Micrometer to Cloud Monitoring and create dashboards for the four golden signals:

  • Latency — p50, p95, p99 of HTTP server requests, broken down by route.
  • Traffic — requests per second, broken down by route and status code.
  • Errors — 5xx rate, broken down by route.
  • Saturation — JVM heap usage, thread pool utilization, connection pool utilization.

If you only ever look at four dashboards, those are the ones.

8. Alert on rate of change, not absolute values

An alert that fires at "5xx rate > 1%" misses gradual degradation and false-positives during normal traffic spikes. Alert on "5xx rate has doubled in the last 5 minutes". You catch the regression sooner and false-positive less.

Secrets and configuration

9. Secret Manager, not env vars in YAML

Use the GCP Secret Manager Spring starter:

spring:
  cloud:
    gcp:
      secretmanager:
        enabled: true

datasource:
  password: ${sm://projects/my-project/secrets/db-password/versions/latest}

Secrets are fetched at startup and cached. Rotation is a Secret Manager version bump plus a pod restart — no code change, no redeploy of new env-var bundles.

10. Workload Identity for service auth

Stop downloading service account JSON keys. Bind the Kubernetes service account to a Google service account via Workload Identity. The pod's GCP API calls authenticate without a key file ever existing on disk.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: orders-api
  annotations:
    iam.gke.io/gcp-service-account: orders-api@my-project.iam.gserviceaccount.com

11. Profile-based config with explicit prod profile

Always run with SPRING_PROFILES_ACTIVE=prod in production. Make the prod profile explicit. Rely on neither defaults nor environment-variable inheritance — both have surprising behavior when something forgets to set them.

Networking

12. Connection pool sizing for backends

The default HikariCP pool is 10 connections. For most services this is fine. For services that fan out to several backends, that pool is shared across all your blocking I/O — including the JDBC connection pool and any internal RestClient pools. Right-size them for your concurrency. A useful starting point:

spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 5000
      idle-timeout: 600000
      max-lifetime: 1800000

The max-lifetime matters for Cloud SQL — proxy connections get reaped server-side after a period of inactivity, and a stale connection in the pool causes the next request to fail with a confusing error.

13. HTTP client timeouts everywhere

The default HTTP client (HttpClient) has no read timeout. A backend that hangs will hang your service indefinitely. Configure timeouts globally:

@Bean
public RestClient restClient() {
    HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(2))
        .build();
    return RestClient.builder()
        .requestFactory(new JdkClientHttpRequestFactory(client))
        .defaultStatusHandler(HttpStatusCode::isError, (req, res) -> { /* logging */ })
        .build();
}

Pair with a per-call read timeout. No client should ever wait forever.

14. Circuit breakers on critical paths

Resilience4j integrates cleanly with Spring Boot. For any backend that is not your own database, wrap calls in a circuit breaker. The default of 50% failure rate over a 100-call window is a reasonable starting point. Tune based on real traffic.

Data

15. Cloud SQL via the connector, not via IP

The Cloud SQL Java connector authenticates via IAM, encrypts in transit, and survives Cloud SQL maintenance windows that would tear down a raw TCP connection. Use it.

spring:
  datasource:
    url: jdbc:postgresql:///mydb?cloudSqlInstance=project:region:instance&socketFactory=com.google.cloud.sql.postgres.SocketFactory&user=svc@my-project.iam&password=ignored

Bonus: combine with Workload Identity and you have passwordless DB auth.

16. Read-only replicas for read-heavy workloads

If your service is read-heavy and your queries can tolerate replica lag of a few hundred milliseconds, route reads to a replica. Spring's AbstractRoutingDataSource does this in 30 lines and removes substantial load from the primary.

17. Migrations run as a separate job, not at startup

Flyway is great. Running migrations during application startup with multiple replicas is not. The first replica races to acquire the migration lock; the others time out and crash. Run migrations as a Kubernetes Job before rolling out the new version of the deployment. The application's Flyway client only verifies the current version on startup.

Autoscaling

18. CPU-based HPA is a starting point, not a finish line

Default to CPU-based autoscaling. For services where the bottleneck is not CPU (request queue depth on an I/O-bound service, for example), add custom metrics. Cloud Monitoring + the GKE custom metrics adapter let you scale on Pub/Sub queue depth, request rate, or anything else Micrometer exposes.

19. PodDisruptionBudget so the cluster cannot evict you to nothing

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: orders-api
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: orders-api

Without a PDB, a node drain (auto-upgrades, autoscaling rebalance) can take all your replicas down at once. With a PDB, the cluster waits for replacements before taking the next pod. This is the cheapest availability improvement on the list.

Deployment

20. Canary deploys with traffic split

The boring version of this: deploy version N+1 alongside N, route 5% of traffic to N+1, watch error rates and latency for 10 minutes, then promote. The infrastructure for this exists on GKE without any service mesh — annotated services and Backend Service traffic splits do the job. The cultural infrastructure is harder; teams resist canary because it slows down deploys. The math says canary saves more time than it costs as soon as it catches one bad deploy per quarter.

The non-negotiables

If you do nothing else from this list, do these five:

  1. Separate liveness and readiness probes.
  2. Graceful shutdown with the matching pre-stop hook.
  3. Structured JSON logging.
  4. HTTP client timeouts on every outbound call.
  5. PodDisruptionBudget on every Deployment.

None of them are sexy. None of them get you a promotion. All of them make the difference between a service that runs in production and a service that runs in production well.

Closing

Production-readiness is not a single decision. It is the accumulation of small ones, each obvious in isolation and easy to skip individually. The cost of skipping shows up later, usually at 3 a.m., usually under load. The checklist exists so you do not have to remember any of this when you are tired.

None of the items above are difficult. The discipline is in walking through all of them every time, even when the service "looks fine".
